# 子智能体调度策略（情况3 结论）

## 一、能加速什么，不能加速什么

**能加速**：IO 密集、可切分、结果可验证的活。

| 任务类型 | 加速比 | 原因 |
|---|---|---|
| 批量 OCR（1281 张面单） | 4-8× | 每张独立，0.56s/张，切 8 份并行 |
| 多服务器目录扫描 | 3-4× | 每台独立 |
| 多格式批量解密尝试 | 4-6× | 每组参数独立 |
| 大日志关键词提取 | 3-5× | 按时间/文件切分 |
| 多份手机备份解析 | 5× | 每个 .bak 独立 |
| 多分支协议解析 | 2-3× | 每种 chunk 类型独立 |

**不能加速**：串行依赖、需要全局判断的活。

| 任务类型 | 为什么不行 |
|---|---|
| 密钥链（root→seed→field_key） | 上一层出不来，下一层无从下手 |
| 「目标事件」锚定 | 需要横向比对多个源，子智能体看不到全局 |
| 口径裁决（第 N 个字段从 0 还是 1 数） | 需要读完整题面 + 交叉验证 |
| 最终答案一致性检查 | 必须主会话做 |
| ext4 journal 恢复 | 单一大文件，无法切分收益 |

## 二、龙信杯实测的时间账

| 任务 | 串行耗时 | 并行耗时 | 说明 |
|---|---|---|---|
| OCR 1281 张面单 | ~12 min | **38 min** | ❌ 更慢——启动开销 + 主会话等结果 |
| 三服务器目录扫描 | ~4 min | ~2 min | ✅ 有效 |
| 流量 4 接口分别解析 | ~6 min | ~2.5 min | ✅ 有效 |
| 门锁 4 模块固件分析 | ~8 min | ~4 min | ✅ 有效 |

**结论**：单个小任务（<5 min）分包是负收益，**启动开销 + 汇总成本大于并行收益**。
只有当单任务 >10 min 且能切成 ≥4 份时才并行。

## 三、判据

```
并行收益 = 单任务时间 × (1 - 1/N) - 启动开销(≈30s) - 汇总成本(≈60s)
```

N=4、单任务 12 min 时：12 × 0.75 - 1.5 = **7.5 min 净收益** ✅
N=4、单任务 3 min 时：3 × 0.75 - 1.5 = **0.75 min，几乎白干** ❌

**判定线：单任务 ≥ 10 min 且可切 ≥ 4 份才分包。**

## 四、正确的分包方式

### 4.1 按数据源切，不按题号切

```
❌ 包1: 题1-10  包2: 题11-20     ← 同一份数据被读 2 次，且互相依赖
✅ 包1: Server01 包2: Server02  包3: 手机备份  包4: 流量
```

### 4.2 每个包必须自包含

```
目标        ：从 Server02 镜像提取全部容器配置与环境变量
检材路径    ：<MOUNT>\Server\Server02.E01，已挂载，LV 起始 LBA 4200448
已知事实    ：Server02 是解密服务器（/opt/query-crypto）
已排除      ：/var/lib/docker/overlay2 已空，镜像层不可用
期望产出    ：CSV，列 = 容器名,镜像标签,Entrypoint,Env(分号分隔),MountPoints
证据要求    ：每行附 config.v2.json 的完整路径
约束        ：只读，输出到 out/srv2_containers.csv
你是叶子节点，不要再委派。
```

### 4.3 子智能体的结论必须抽验

子智能体会**自信地把字符串里的提示文字当成真实字段名**。实测案例：

- 把 `"   Set-Disk -Number 1 -IsOffline $true"` 判成高危操作
- 把 `eject-probe.ps1` 的 `Stop-Process` 说成 `fast-copy-optimize.ps1` 的
- 报了 12 个"密钥候选"，其中 8 个是它从注释里读出来的

**抽验规则**：子智能体报的每个关键值，主会话必须自己 `read`/`grep` 那一处确认。
龙信杯的 Q29 端口就是信了子智能体的"257"，实际是 911。

## 五、workflow 适合什么

块数 ≥ 8 或同一模板批量跑时用 `workflow` + `pipeline`：

```js
const r = await pipeline(
  files,
  f => agent(`解析 ${f} 的所有 FDM4 记录，输出 JSON：字段名→值`, { schema: {...} }),
  (parsed, f) => agent(`校验 ${f} 的解析结果，逐字段复算校验和`)
)
```

龙信杯适用场景：15 个 .bak 文件各提一次 sp/ 配置、1281 张面单分批 OCR、
8 个控制会话各算一次摘要链。

## 六、不该分包的信号

- 任务需要**看全局才能判断**（哪个是"目标事件"、哪个是"真实控制端"）
- 任务是**串行链**（密钥派生、逐层解包）
- 单任务 **< 10 min**
- 结果是**一个数字**（分包后还要合并，收益为零）
- 涉及**写同一文件**（会冲突）

## 七、本会话的实测建议

龙信杯 75 题，正确做法是：

```
主会话先做（30 min）：
  1. toolcheck 自检
  2. 读题分组 → 源×题矩阵
  3. 清点 6 个检材的结构
  4. 判定哪些包值得分

并行包（≥4 个，每个 >10 min）：
  包A  Server01 全部（目录树 + 配置 + 日志）
  包B  Server02 全部（同）
  包C  手机 15 个 .bak 的 sp/ 提取
  包D  流量 4 接口的协议族统计

主会话留（必须自己做）：
  - 密钥链攻击（串行）
  - 目标事件锚定（看全局）
  - 口径裁决
  - FINAL.md 一致性核对
```
