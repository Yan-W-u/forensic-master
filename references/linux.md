# Linux 取证手册

## 一、挂载与访问

```python
from forensic import Evidence, Walk
ev = Evidence(r"镜像.e01")
fs = ev.volumes["part3:Linux (0x83)"]     # 标签含 "Linux"
w = Walk(fs)
```

注意 MBR 分区类型：`0x83` = Linux，`0x0c` = FAT32（常见于树莓派启动分区）。

## 二、系统标识

| 题目问什么 | 文件 | 坑 |
|---|---|---|
| 主机名 | `/etc/hostname` | |
| 发行版 ID | `/usr/lib/os-release` 的 `ID=` | **`/etc/os-release` 常是符号链接**，直读得全 `\x00` |
| 发行版本号 | `/usr/lib/os-release` 的 `VERSION_ID=` | 同上 |
| Debian 版本 | `/etc/debian_version` | |
| 时区 | `/etc/timezone` | 也可能是 `/etc/localtime` 符号链接 |
| machine-id | `/etc/machine-id` | 32 位小写 hex |
| PARTUUID | `/etc/fstab` | 启动分区通常 `-01` |
| DNS | `/etc/resolv.conf` | 第 2 个 nameserver 是"备用" |
| 用户主组 GID | `/etc/passwd` 第 4 字段 | |
| 登录 shell | `/etc/passwd` 第 7 字段 | 非 `/usr/sbin/nologin` 才可登录 |

**关键坑**：`/etc/os-release` 在很多镜像里是指向 `/usr/lib/os-release` 的符号链接，用 TSK 直接 `read_random` 会读到 21 个 `\x00` 字节（因为 TSK 不解符号链接）。必须读真实路径。

## 三、账号与密码

### 3.1 shadow 解析

`/etc/shadow` 格式：
```
用户名:$算法$盐$哈希:最后改密天数:最小间隔:最大间隔:警告天数:失效天数:保留
```

算法前缀：

| 前缀 | 算法 | 题面应填 |
|---|---|---|
| `$1$` | MD5 | md5 |
| `$5$` | SHA-256 | **sha256** |
| `$6$` | SHA-512 | sha512 |
| `$y$` | yescrypt | yescrypt |
| `$2b$` | bcrypt | bcrypt |
| `!` 或 `*` | 锁定 | — |

**坑**：`$5$` 是 SHA-256 不是 SHA-512，容易看反。

盐值取 `$5$` 和下一个 `$` 之间的字符串。

### 3.2 改密日期

第 3 字段是"1970-01-01 起的天数"：
```python
import datetime
date = datetime.date(1970,1,1) + datetime.timedelta(days=int(field))
```

## 五、内核与硬件

| 题目问什么 | 位置 |
|---|---|
| 树莓派型号 | `/var/log/kern.log`、`syslog` 的 `Machine model: Raspberry Pi 5 Model B Rev 1.1` |
| 硬件修订版 | 同上，取 `Rev X.Y` |
| 内核版本 | `uname -r` 的输出，或在 `/lib/modules/` 下 |
| Uptime/启动时间 | `uptime`、`/proc/uptime` |

**坑**：树莓派可能换过板，`syslog.1` 里是旧型号、`syslog` 里是新型号。攻击相关时段用哪个型号要按时间对齐。

## 六、服务与日志

### 6.1 journald

`/etc/systemd/journald.conf`：
```ini
Storage=persistent      # 持久化到 /var/log/journal
```

题面若问"推荐做法新增 drop-in"→ `/etc/systemd/journald.conf.d/`（注意不是 `/etc/systemd/system/journald.service.d/`）

重启命令：`sudo systemctl restart systemd-journald`

### 6.2 audit

`/etc/audit/audit.rules`、`/etc/audit/rules.d/*.rules`

常见参数：
- `-b 8192` 缓冲队列上限
- `--backlog_wait_time 60000` 等待毫秒
- `-k file_activity` 规则键名

**坑**：`audit.rules` 首行常写 `-D` 和 `# This file is automatically generated from /etc/audit/rules.d`。题目若问"规则来源目录"，看的是**注释里的路径**，容易多抄一个 `/var/log/`。

## 七、Shell 配置

### 7.1 HISTSIZE / HISTFILESIZE

`~/.bashrc`：
```bash
HISTCONTROL=ignoreboth    # 忽略重复 + 忽略空格开头
shopt -s histappend       # 追加而非覆盖
HISTSIZE=1000             # 内存缓冲
HISTFILESIZE=2000         # 磁盘文件上限
```

对照题面说法逐条判：
- "内存 1000 条" → `HISTSIZE=1000` ✅
- "磁盘 2000 条" → `HISTFILESIZE=2000` ✅
- "覆盖而非追加" → 错（`histappend` 是追加）❌
- "完整记录重复命令和空格开头" → 错（`ignoreboth` 会忽略）❌

### 7.2 PROMPT_COMMAND

`/etc/bash.bashrc`：
```bash
PROMPT_COMMAND='echo -ne "\033]0;${USER}@${HOSTNAME}: ${PWD}\007"'
```

`${PWD}` 是**绝对路径**，`\w` 才会显示 `~`。所以停在主目录时标题是 `/home/username` 而不是 `~`。

## 九、攻击工具痕迹

### 9.1 终端会话日志

`/root/terminal-logs/*.log`、`/var/log/terminal_sessions/*/`

常见关键词：
- `Starting de-auth loop...` 正式开始发包
- `Setting channel -> N` 切信道
- `Choose a target from 1 to N:` 等用户选择（此时可能被 Ctrl+Z 挂起）

统计"正式发包循环次数"时，只数 `Starting de-auth loop` 之后的，**扫描阶段的 `Scanning channel` 不算**。

### 9.2 git 痕迹

`.git/logs/HEAD` 每行含 epoch 时间戳，可判断首次 clone 时间：
```
0000000 abc <a@b> 1785744125 +0800  clone: from https://...
```

## 十、Docker 与容器

### 10.1 容器配置（最可靠，常在）

`/var/lib/docker/containers/<64hex>/config.v2.json`：

```python
import json
for d in os.listdir('/var/lib/docker/containers'):
    j = json.loads(read('/var/lib/docker/containers/%s/config.v2.json' % d))
    print(j['Name'])                                   # /dqmain-gate-1
    print(j['Config']['Image'])                        # dqmain/app-runtime:3.4.6-keyfix1
    print(j['Path'], j['Args'])                        # Entrypoint + Cmd
    print(j['Config']['Env'])                          # 全部环境变量
    for k, v in (j['Config']['Labels'] or {}).items():
        if 'compose' in k: print('  ', k, '=', v)
```

`com.docker.compose.*` 标签能还原出：

| 标签 | 用途 |
|---|---|
| `com.docker.compose.project` | compose 项目名（= 容器名前缀） |
| `com.docker.compose.service` | 服务名（容器名 = `<project>-<service>-<num>`） |
| `com.docker.compose.image` | **镜像 digest**（sha256:...） |
| `com.docker.compose.project.config_files` | compose 文件路径 |
| `com.docker.compose.depends_on` | 启动依赖顺序 |

**判据**：题面问「容器名」「镜像标签」「挂载路径」「启动顺序」→ 全部能从 `config.v2.json` + `docker-compose.yml` 得到，**不需要镜像层**。

### 10.2 镜像层的现实

```python
# 先确认还在不在
ls('/var/lib/docker/image/overlay2')      # repositories.json / imagedb / layerdb
ls('/var/lib/docker/overlay2')            # 各层 merged/diff
ls('/var/lib/docker/rootfs/overlayfs')
```

**这三种目录为空是常态**（比赛做检材时常清理镜像省空间）：

```
/var/lib/docker/overlay2/          → 空 → 没有镜像层，无法读容器内文件
/var/lib/docker/image/overlay2/    → 空 → 没有 repositories.json，拿不到 tag→digest 映射
/var/lib/docker/rootfs/overlayfs/  → 空
```

**遇到空的处理**：

1. 镜像标签从哪来？→ `docker-compose.yml` 的 `image:` 行（明文）+ `config.v2.json` 的 `Config.Image`
2. 容器内源码从哪来？→ compose 的 `volumes:` 挂载路径（宿主机侧目录）
3. 都拿不到 → 标 ⬜「镜像层已删，源码级取证不可行」

龙信杯就是这种情况：`dqmain/app-runtime:3.4.6-keyfix1` 的源码在 `/run/dq-runtime/app`（tmpfs，运行时生成，已随关机丢失），镜像里本来也不含完整源码——题面正是问这个。

### 10.3 `/var/lib/docker/image/identity-cache.db`

二进制缓存（魔数 `image-identity-cache-v1`），内含 `sha256:xxx|sha256:yyy|linux/amd64{JSON}` 形式的 digest 对，**不含 tag 名**。可用来核对 digest，不能反查 tag。

### 10.4 网络

- `172.18.0.1` → Docker 网桥网关（宿主机侧）
- `172.18.0.x` → 容器 IP
- `192.168.x.x` → 物理内网

pcap 里看到 `172.18.0.x` 说明是 Docker 网络。

### 10.5 systemd 与 Docker 的联动（题常问）

```ini
[Unit]
Requires=docker.service
After=docker.service
PartOf=docker.service          ← 停 docker 时连带停本服务

[Service]
Type=oneshot                   ← 一次性脚本（常见于 bootstrap/init）
RemainAfterExit=yes            ← 脚本退出后服务状态仍算 active
ExecStart=/opt/xxx/bin/start
ExecStop=/opt/xxx/bin/stop
ExecStopPost=/usr/local/libexec/cleanup    ← 服务停止后的清理钩子（反取证常在这里）

[Install]
WantedBy=multi-user.target
```

**判据**：
- 问「启动某业务的服务名」→ 找 `ExecStart=` 指向该业务脚本的 `.service`
- 问「服务实际执行的宿主机程序」→ 就是 `ExecStart=` 的路径（**注意可能是包装脚本，见下**）
- 问「清理时先停什么」→ 看 `ExecStopPost=` 指向的脚本里的顺序

### 10.6 包装脚本 vs 真实二进制

```bash
#!/usr/bin/env bash
CORE="${DQ_AGENT_CORE:-$BASE/bin/crypto-agent.core}"
"$CORE" "$@" &
wait "$child"
"$CLEANUP" "agent-exit-rc-${agent_rc}"
```

`ExecStart` 指的是 **wrapper**（`crypto-agent`），真正干活的是它 exec 的 **core**（`crypto-agent.core`）。题面问「原始核心启动程序」→ 填 core 的路径。

**判据**：脚本里出现 `exec`、`"$CORE"`、`${XXX_CORE:-...}` 这类模式，就去找那个真实二进制。

### 10.7 反取证清理脚本的读法

`ExecStopPost` 指向的 cleanup 脚本，注释里直接写清理顺序：

```bash
# 1) Gate must stop first.
stop_service gate
# 2) Then app.
stop_service app
# 3) Verify port 80 is closed before runtime destruction.
# 4) Only after the stop/port-close phase, clear runtime plaintext.
find "$RUNTIME" -mindepth 1 -maxdepth 1 -exec rm -rf -- {} +
```

**判据**：题面问「最先被停止的容器」→ 看 `stop_service` 的调用顺序第一条，容器名拼成 `${PROJECT}-${svc}-1`（`PROJECT` 是 compose 项目名，常在脚本顶部 `PROJECT="${DQ_PROJECT:-dqmain}"`）。

## 十二、目录遍历失败的坑

TSK 对某些目录（如 `/etc/nginx`）会报 `Unable to open directory: Invalid API argument`，通常是因为：

1. 该路径实际不存在
2. 符号链接未解析
3. 目录项损坏

**处理**：用 `Walk.ls_safe()` 并检查 `w.errors`，**不要静默跳过**。本次实战就因为跳过了桌面目录，漏掉 `nginx-tronic.conf`，导致 Q103 答错。

## 十三、先判断二进制是什么语言（反汇编前必做）

同一套服务里的多个二进制**可能用不同语言写**。龙信杯实测：`kms`、`gateway-401` 是 **Go**，而 `crypto-agent.core` 是 **Rust**。按 Go 的思路去啃 Rust 二进制，会白找半天 `gopclntab`。

### 13.1 三条判据

| 判据 | Go | Rust |
|---|---|---|
| 符号形态 | `main.(*server).decrypt`、`meridian.local/core/...`（**带点、带斜杠路径**） | `_ZN4core5slice4sort6stable5drift4sort17ha4603ff3bb8b637bE`（**`_ZN...E` mangled**） |
| 源码路径串 | `/usr/local/go/src/...`、包名点分 | **`/rustc/<40位hash>/library/alloc/src/...`** |
| 独有串 | `runtime.mallocgc`、`gcphase`、`boringcrypto` | `called 'Result::unwrap()' on an 'Err' value`、`internal error: entered unreachable code`、`assertion failed: ...` |

### 13.2 一条命令区分

```powershell
& 'E:\bianyiqi\mingw64\bin\strings.exe' -n 6 -t d 'app.bin' |
  Select-String -Pattern '/rustc/|_ZN.*17h[0-9a-f]{16}E|runtime\.mallocgc|gopclntab' |
  Select-Object -First 5
```

命中 `/rustc/` 或 `_ZN...17h<hash>E` → **Rust**；命中 `runtime.` / `gopclntab` → **Go**。

### 13.3 两种语言各自的提效手法

**Go**
- `strings` 直接出可读符号（`主包.类型.方法`），能把函数名当索引
- 结构体字段名**连成一串**输出，形如
  ```
  struct Config with 12 elements node_id challenge_id dataset_id schema_rev
  generation db_generation manifest_hash runtime_epoch crypto_endpoint
  renew_interval grace_deadline server_cert_pin
  ```
  → **字段名和顺序直接可读**，这是 Go 二进制的最大优势
- `go tool objdump` / `go tool nm` 可直接反汇编

**Rust**
- 符号是 `_ZN` mangled，用 `rustfilt` 还原：`cargo install rustfilt` 或在线 demangle
- 但**结构体字段名同样连串输出**（Rust 的 `Debug` 派生会把字段名编译进去），上面那段 Config 就是从 Rust 二进制里读出来的
- `/rustc/<hash>/` 路径能确定编译器版本
- 关键串常成组出现，形如
  ```
  struct AcquireResp with 8 elements  expires_at server_ephemeral_pub seal_nonce
  sealed_key_bundle server_nonce timestamp ...
  struct Bundle with 6 elements  app_dek runtime_seed ...
  ```
  → **拿到这些就等于拿到了协议定义**

### 13.4 从字符串还原协议的实操

```powershell
# 一次性把「结构体定义」全捞出来
& 'E:\bianyiqi\mingw64\bin\strings.exe' -n 8 -t d 'app.bin' |
  Select-String -Pattern 'struct \w+ with \d+ elements' |
  Select-Object -First 20
```

输出会是连续的字段名串，按 `with N elements` 的 N 切分即可。配合 HTTP 路径串（`/v1/lease/acquire`、`/v1/lease/renew`）就能画出完整接口。

**判据**：题面问「第 N 个字段名」「签名算法」「时间容差」→ 先做这一步，多数情况下**不用反汇编就能答**，因为字段名和常量都以明文躺在 `.rodata` 里。

### 13.5 配置项 vs 协议常量

配置 JSON 里的值（如 `grace_deadline=90`、`lease_ttl=120`、`renew_interval=60`）**不一定是题面问的那个数**。

题面问「请求时间与服务器时间允许相差最大秒数」时：
- `grace_deadline` 是**业务宽限**（续租失败后还能用多久）
- `lease_ttl` 是**授权有效期**
- 真正的时钟容差通常写在代码里，是硬编码常量或另一份 schema 文件

**判据**：先在 strings 里搜 `skew` / `tolerance` / `clock` / `drift` 的**上下文**，找不到再去反汇编比较 `SystemTime::now()` 附近的比较常量。**不要直接拿配置 JSON 里的数字填。**


## 十四、计划任务（cron / systemd timer / at）

**题常问**：「哪个任务在几点跑」「这个脚本被谁定时调用」「第一次执行时间」。

### 14.1 五个位置，一个都不能漏

| 位置 | 说明 |
|---|---|
| `/etc/crontab` | 系统级，**带用户名段**（6 段式） |
| `/etc/cron.d/*` | 同上，**带用户名段** |
| `/etc/cron.{hourly,daily,weekly,monthly}/` | 放脚本，**无时间字段**（由目录名决定周期） |
| `/var/spool/cron/crontabs/<user>` | 用户级（Debian），**5 段式，无用户名** |
| `/var/spool/cron/<user>` | 用户级（RHEL） |
| `/etc/anacrontab` | anacron，与 cron 不同格式 |

**判据**：段数决定是谁的 crontab。
```
5 段 = 用户 crontab（分 时 日 月 周 命令）
6 段 = 系统 crontab（分 时 日 月 周 用户 命令）
```

### 14.2 解析

```python
import re

def parse_cron(line):
    s = line.strip()
    if not s or s.startswith('#'):
        return None
    # 处理环境变量行
    if '=' in s and not s[0].isdigit() and not s[0] in '*@':
        return ('ENV', s)
    m = re.match(r'^(\S+)\s+(\S+)\s+(\S+)\s+(\S+)\s+(\S+)\s+(.*)$', s)
    if not m:
        return None
    f = m.groups()
    cmd = f[5]
    # 6 段：第 6 个字段若不含 / 且短，可能是用户名
    user = None
    parts = cmd.split(None, 1)
    if len(parts) == 2 and re.fullmatch(r'[a-z_][a-z0-9_-]{0,31}', parts[0]):
        user, cmd = parts
    return dict(minute=f[0], hour=f[1], dom=f[2], month=f[3], dow=f[4],
                user=user, cmd=cmd)
```

**`@reboot` / `@daily` / `@hourly` 这类简写**要单独处理：

```python
SPECIAL = {'@reboot': '每次启动', '@yearly': '每年', '@annually': '每年',
           '@monthly': '每月', '@weekly': '每周', '@daily': '每天',
           '@midnight': '每天0点', '@hourly': '每小时'}
```

### 14.3 反取证线索：cron 被改过的痕迹

```python
# 看 mtime，任务文件的修改时间说明"什么时候被动过"
for p in ('/etc/crontab', '/var/spool/cron/crontabs/root'):
    m = fs.open(p).info.meta
    print(p, m.mtime, m.ctime)
```

**判据**：`crontab` 的 mtime 比 `/etc/passwd` 晚很多，且内容含 `curl | sh`、`base64 -d`、
`/dev/tcp/`、`nc -e` → 是后门，不是正常运维。

```python
BACKDOOR = ['curl', 'wget', 'base64 -d', '/dev/tcp/', 'nc -e', 'bash -i',
            'python -c', 'perl -e', 'xxd -r', 'chmod +x /tmp']
for line in open('/etc/crontab'):
    if any(k in line for k in BACKDOOR):
        print('!', line.strip())
```

## 十五、Shell 历史（bash_history）深度用法

**题常问**：「嫌疑人在服务器上执行了什么」「最后一次命令是什么」「下载了什么工具」。

### 15.1 文件位置

| 文件 | 说明 |
|---|---|
| `~/.bash_history` | bash 默认，**退出时才写入**，可能不全 |
| `~/.zsh_history` | zsh（带时间戳格式不同） |
| `~/.python_history` | python REPL |
| `~/.mysql_history` | mysql |
| `~/.psql_history` | psql |
| `~/.lesshst` | less |
| `~/.viminfo` | vim（含打开过的文件） |
| `~/.sqlite_history` | sqlite3 |
| `/root/.bash_history` | root 的 |

**坑**：`~/.bash_history` 只有在 shell **正常退出**时才写盘。非正常退出（kill -9、断电）
会丢最后一段。此时要看：

```python
# 1) 进程内存（若有内存镜像）
# 2) audit 日志
# 3) 终端的 tty 记录：/var/log/btmp、wtmp
# 4) 屏幕录制/会话日志：/var/log/script/*
```

### 15.2 带时间戳的 history

如果 `/etc/bash.bashrc` 或 `~/.bashrc` 里有：

```bash
HISTTIMEFORMAT="%F %T "
```

则 `.bash_history` 里每条命令前会有一行 `#<epoch>`：

```
#1788472800
ls -la /opt
#1788472815
cat /etc/passwd
```

```python
import datetime, re

def parse_history_timed(path):
    lines = open(path, encoding='utf-8', errors='replace').read().splitlines()
    out, ts = [], None
    for ln in lines:
        if ln.startswith('#') and ln[1:].isdigit():
            ts = int(ln[1:])
        elif ln.strip():
            out.append((datetime.datetime.fromtimestamp(ts, datetime.timezone.utc) if ts else None, ln))
            ts = None
    return out
```

**判据**：没有 `#` 行 = 未开时间戳，只能按顺序推（相邻命令时间差不可知）。

### 15.3 zsh 的格式

```
: 1788472800:0;ls -la /opt
  ^epoch      ^耗时  ^命令
```

```python
PAT = re.compile(r'^: (\d+):(\d+);(.*)$')
```

### 15.4 从 history 反推攻击链

```python
SUSPICIOUS = {
    '下载': ['wget', 'curl', 'scp', 'rsync', 'git clone'],
    '提权': ['sudo', 'su -', 'chmod +s', 'find / -perm -4000'],
    '持久化': ['crontab', 'systemctl enable', '>> ~/.bashrc', '/etc/rc.local'],
    '横向': ['ssh ', 'sshpass', 'proxychains', 'nmap', 'masscan'],
    '打包外传': ['tar czf', 'zip -r', 'base64', 'split', 'nc -'],
    '清理': ['shred', 'rm -rf', 'history -c', 'unset HISTFILE', '> ~/.bash_history'],
}
for ts, cmd in parse_history_timed('/root/.bash_history'):
    for cat, keys in SUSPICIOUS.items():
        if any(k in cmd for k in keys):
            print('%s [%s] %s' % (ts or '-', cat, cmd))
            break
```

**判据**：出现 `history -c`、`unset HISTFILE`、`rm ~/.bash_history`、`ln -s /dev/null ~/.bash_history`
→ 明确的清除历史行为，要在结论里写清「证据被主动销毁」。

### 15.5 HISTFILE 被改成 /dev/null

```bash
# ~/.bashrc 里
export HISTFILE=/dev/null
export HISTSIZE=0
```

**判据**：`~/.bashrc` 里出现这些 → 历史上限被关掉，`.bash_history` 会是空或不更新。
此时只能靠 auditd 或 `/var/log/auth.log` 的 sudo 记录还原。

## 十六、SSH 取证

**题常问**：「谁登录过」「从哪个 IP」「用了什么密钥」「失败多少次」。

### 16.1 认证日志

| 文件 | 内容 |
|---|---|
| `/var/log/auth.log`（Debian） | SSH 登录、sudo、su |
| `/var/log/secure`（RHEL） | 同上 |
| `/var/log/btmp` | **失败**登录（二进制） |
| `/var/log/wtmp` | **成功**登录与登出（二进制） |
| `/var/log/lastlog` | 每个用户最后登录（二进制） |
| `~/.ssh/authorized_keys` | 允许登录的公钥（后门常在这里） |
| `~/.ssh/known_hosts` | 连出去过的主机 |
| `/etc/ssh/sshd_config` | 端口、是否允许 root、密码登录开关 |

### 16.2 auth.log 解析

```python
import re

PATS = {
    'ok':     re.compile(r'Accepted (\S+) for (\S+) from ([\d.]+) port (\d+)'),
    'fail':   re.compile(r'Failed (\S+) for (invalid user )?(\S+) from ([\d.]+)'),
    'invalid':re.compile(r'Invalid user (\S+) from ([\d.]+)'),
    'sudo':   re.compile(r'sudo:\s+(\S+) : .*COMMAND=(.*)$'),
    'session':re.compile(r'session (opened|closed) for user (\S+)'),
}
for ln in open('/var/log/auth.log', encoding='utf-8', errors='replace'):
    for k, p in PATS.items():
        m = p.search(ln)
        if m:
            print(k, m.groups())
            break
```

**切记**：`Accepted publickey for root from 1.2.3.4` 说明**用密钥**登录
（`password` 才是密码）。题问「登录方式」时这个区别是答案。

### 16.3 wtmp / btmp（二进制，别当文本读）

```python
import struct, datetime

WTMP_FMT = '<hh32s4s32s256shhiii4i20s'   # Linux utmp 结构
WTMP_SIZE = 384

def parse_wtmp(path):
    out = []
    with open(path, 'rb') as f:
        while True:
            rec = f.read(WTMP_SIZE)
            if len(rec) < WTMP_SIZE:
                break
            ut_type, ut_pid, ut_line, ut_id, ut_user, ut_host, \
                e_termination, e_exit, tv_sec, tv_usec, \
                a1, a2, a3, a4, session = struct.unpack(
                    '<h2s32s4s32s256shhiii4s4s4s4s4s', rec) if False else (None,)*15
            # 简化：只取关键字段
            ut_type = struct.unpack('<h', rec[0:2])[0]
            ut_user = rec[44:76].split(b'\x00')[0].decode('utf-8', 'replace')
            ut_host = rec[76:332].split(b'\x00')[0].decode('utf-8', 'replace')
            tv_sec = struct.unpack('<i', rec[340:344])[0]
            out.append(dict(type=ut_type, user=ut_user, host=ut_host,
                            time=datetime.datetime.fromtimestamp(tv_sec, datetime.timezone.utc) if tv_sec else None))
    return out
```

**ut_type 取值**：

| 值 | 含义 |
|---|---|
| 7 | `USER_PROCESS` **登录** |
| 8 | `DEAD_PROCESS` **登出** |
| 6 | `LOGIN_PROCESS` |
| 2 | `BOOT_TIME` 开机 |

**判据**：算在线时长 = `DEAD_PROCESS.time - USER_PROCESS.time`，按 `ut_line`（tty）配对。

### 16.4 authorized_keys 后门排查

```python
import base64, binascii

for key in open('/root/.ssh/authorized_keys').read().splitlines():
    if not key.strip() or key.startswith('#'):
        continue
    parts = key.split()
    b64 = [p for p in parts if len(p) > 50 and not p.startswith('ssh-')][0]
    blob = base64.b64decode(b64)
    # 取注释（末尾的可读串）
    tail = blob[-64:].split(b'\x00')[0]
    print('%-12s %-40s %s' % (parts[0], tail.decode('utf-8','replace'),
                              parts[-1] if parts[-1] != b64 else ''))
```

**判据**：`authorized_keys` 的 mtime 很新 + 有陌生公钥 → 是后门。
配合 `auth.log` 看这个 key 有没有被用过（`Accepted publickey`）。

### 16.5 sshd_config 关键项

```
Port 22                     ← 端口（题问"SSH 端口"就查这个）
PermitRootLogin yes         ← 允许 root 直登（危险配置）
PasswordAuthentication no   ← 只允许密钥
AllowUsers alice bob        ← 白名单
MaxAuthTries 6
```

**判据**：问「SSH 监听端口」→ `Port`；问「是否允许密码登录」→ `PasswordAuthentication`。
**不要**从 `netstat` 历史里猜，配置文件的 `Port` 才是准的。

## 十七、反取证痕迹识别（服务器侧）

服务器类题目越来越爱考「嫌疑人做了什么掩盖」。以下是龙信杯实测到的真实手法。

### 17.1 日志被关闭

```nginx
# /opt/delivery-query/gate.conf  ← 不在 /etc/nginx，藏在应用目录
http {
  access_log off;                  ← 不记录访问日志
  error_log /dev/null crit;        ← 错误日志丢弃
}
```

**判据**：`access_log off` / `error_log /dev/null` / `error_log syslog:server=...`

**为什么要藏在应用目录**：正常 nginx 配置在 `/etc/nginx`，这里放在 `/opt/<app>/gate.conf`，
用 `ls /etc/nginx` 找不到。**必须在 /opt、/usr/local、/srv、/data 下递归找 `*.conf`。**

### 17.2 Shell 历史被清

龙信杯实测 `.bash_history`（4 行，全是清理动作）：

```bash
sudo bash -c 'history -c; rm -f /root/.bash_history /home/*/.bash_history /home/*/.zsh_history'
unset HISTFILE; export HISTSIZE=0 HISTFILESIZE=0
```

**判据**：这四条命令本身就是证据。要在结论里写「**证据被主动销毁**」，而不是「没有历史记录」。

其他清理手法：

```bash
ln -sf /dev/null ~/.bash_history      # 软链到空设备
export HISTFILE=/dev/null             # 重定向
shred -n 0 -z -u ~/.bash_history      # 覆写擦除
echo "" > ~/.bash_history             # 清空
```

### 17.3 用 shred 擦除整个目录

龙信杯 `auth.log` 实录：

```
2026-09-01T09:57:53  find /home/goyasha -xdev -type f -exec shred -n 0 -z -u -- {} +
2026-09-01T09:57:53  find /home/goyasha -xdev -mindepth 1 -delete
2026-09-02T07:42:20  find /home/goyasha -xdev -type f -exec shred -n 0 -z -u -- {} +
2026-09-02T07:42:21  find /home/goyasha -xdev -mindepth 1 -depth -delete
```

**`shred -n 0 -z -u` 的含义**：
```
-n 0   不覆写（但后面 -z 会覆写一次 0）
-z     最后用 0 覆写一遍，掩盖痕迹
-u     覆写后删除
```

**判据**：`-xdev` 限定同一文件系统（避免跨挂载点）、`-mindepth 1` 保留父目录本身。
这条命令**擦两遍**，文件内容基本不可恢复。

**能恢复什么**：
- ext4 journal 的**元数据**（文件曾经存在过、inode、大小）
- 目录项的**文件名**
- 文件系统的 **mtime/ctime**（父目录的修改时间）

**不能恢复什么**：文件正文（数据块已被 0 覆写）。

### 17.4 sudo 记录是反取证的天敌

**关键**：`shred` 需要 root，而 `sudo` 会记日志。龙信杯 `auth.log` 完整留下了：

```
2026-09-02T07:32:33  /usr/local/bin/qdec /home/goyasha/pckey.qenc
2026-09-02T07:35:29  install python3-pycryptodome 3.20.0     ← dpkg.log
2026-09-02T07:41:27  /home/goyasha/query-crypto-docker-simple-v4.1/install.sh
2026-09-02T07:42:20  find /home/goyasha -type f -exec shred ...
2026-09-02T07:42:29  /usr/local/bin/qdec /home/goyasha/pckey.qenc
```

**从时间线能还原整个操作序列**，即使文件被擦。这是服务器取证最重要的一条：
**先看 `/var/log/auth.log` 的 `COMMAND=` 行，再看文件系统。**

```python
import re
for ln in open('/var/log/auth.log', encoding='utf-8', errors='replace'):
    m = re.search(r'(\S+)\s+sudo:\s+(\S+) : .*COMMAND=(.*)$', ln)
    if m:
        print(m.group(1), '|', m.group(2), '|', m.group(3)[:120])
```

### 17.5 临时安装的包暴露操作意图

`dpkg.log` 里「现装现用」的包往往是关键线索：

```
07:35:29  install python3-pycryptodome:amd64 3.20.0   ← 写了加密/解密脚本
```

**判据**：包的安装时间与其他操作紧邻（前后 10 分钟内）→ 说明是为了当时的某个临时目的装的。

常见「意图暴露包」：

| 包 | 意图 |
|---|---|
| `python3-pycryptodome` / `python3-cryptography` | 写加解密脚本 |
| `gcc` / `make` | 编译 exploit 或工具 |
| `nmap` / `masscan` | 扫描 |
| `socat` / `netcat` | 反弹 shell |
| `openssl` | 证书/加解密 |
| `strace` / `ltrace` | 调试/反调试 |

### 17.6 Docker 层被删

```
/var/lib/docker/overlay2/          空
/var/lib/docker/image/overlay2/    空
/var/lib/docker/rootfs/overlayfs/  空
```

**含义**：镜像层被清理，容器内文件不可读。

**还能拿什么**：
- `containers/*/config.v2.json` —— 容器名、镜像标签、全部 Env、挂载点
- `containers/*/hostconfig.json` —— 资源限制、网络模式
- `volumes/metadata.db` —— 卷的元数据
- **宿主机侧的 bind mount 源目录**（`MountPoints` 里的 `Source`）—— 这往往是源码

**判据**：题问「容器内某文件」→ 若 overlay2 空，去 `MountPoints` 找宿主机侧对应目录。

### 17.7 反取证检查清单

```
□ /var/log/auth.log 的 COMMAND= 全提过
□ dpkg.log 的 install 时间线与操作对齐
□ .bash_history 里有没有 history -c / unset HISTFILE / shred
□ 有没有 find ... -exec shred / rm -rf 记录
□ nginx 配置：access_log off / error_log /dev/null
□ 非标准位置的 *.conf（/opt、/usr/local、/srv、/data）
□ docker overlay2 是否为空
□ 关键目录的 mtime 是否异常新（说明最近被动过）
```
